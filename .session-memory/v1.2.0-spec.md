## Feature 1: `--help` with inline examples

**What:** Add 3-5 short examples to `png2svg --help` output, below the
existing epilog (presets block). Use the existing `epilog=` field or
add a new one.

**Examples to include:**
1. `png2svg photo.jpg out.svg` — quick default conversion
2. `png2svg drawing.png out.svg --preset logo --line-step 2` — preset + override
3. `png2svg photo.jpg out.svg --palette-file markers.json` — custom marker palette
4. `png2svg photo.jpg out.svg --split-layers --preview` — split + preview
5. `png2svg photo.jpg out.svg --save-session && png2svg photo.jpg out2.svg --use-session out.session.json` — session reproducibility

**Format:** Triple-backtick code blocks. 2-3 lines per example
(comment + command).

**Acceptance:**
- `png2svg --help` shows the examples after the presets block
- Layout doesn't break with terminals wider than 80 cols
- No regression in existing --help tests

**Files touched:** `src/png2svg/cli.py` only.

## Feature 2: `--preview`

**What:** After successful render, open the output SVG in the system's
default viewer.

**CLI:**
```
--preview    Open output SVG in default viewer after render
```

**Implementation:**
```python
import webbrowser
if a.preview:
    webbrowser.open(output_path.resolve().as_uri())
```
At the end of `main()`, after the render succeeds. Only open the
main output; do not open split-layer files (would be spammy).

**Edge cases:**
- On Linux without a DISPLAY: log a warning, don't fail
- `--preview` + `--split-layers`: open only the main output (warn
  if --split-layers is also set)
- Failed render: don't open anything

**Acceptance:**
- Flag exists in `--help`
- Code uses `webbrowser.open()` (stdlib only)
- No regression in existing tests

**Files touched:** `src/png2svg/cli.py`, possibly add
`tests/integration/test_cli.py::test_cli_preview_flag_parsed`.

## Feature 3: `--split-layers`

**What:** Write one SVG file per color layer, instead of all layers
in a single file. Naming: `<stem>_<NN>_<marker_name>.svg` where NN
is the layer index (zero-padded), e.g. `out_00_red.svg`,
`out_01_blue.svg`. The main output file is still written with all
layers combined (existing behavior preserved).

**CLI:**
```
--split-layers    Also write one SVG file per color layer to <stem>_<NN>_<color>.svg
```

**Naming sanitization:** Marker names can contain spaces and special
characters. Sanitize for filesystem: lowercase, replace whitespace
and any char not in `[a-z0-9_-]` with `_`, collapse runs of `_`.

**Layer ordering:** Match the order they appear in the rendered
output (which is determined by `process_image_to_hatched_svg`'s
internal layer list).

**Implementation hint:** `process_image_to_hatched_svg` returns
`color_map_used` which has one entry per generated layer. The
`processing_stats["layer_stats"]` list also has one entry per layer
in render order. To get the actual SVG content per layer, we need
either:
- (a) Refactor `process_image_to_hatched_svg` to optionally return
  per-layer SVG strings, OR
- (b) Re-render each layer individually post-hoc using a new
  helper `render_layer_to_svg(idx, rgb, mask, params, ...)`.

**Recommendation:** Option (b). It's a pure addition — no signature
change to the existing function, no risk of regression. The helper
takes the same args as `_process_single_layer` minus the
marker_counters (which we can recompute).

**Edge cases:**
- Layer with no marker name: use `unnamed` as the slug
- Color name collision (two layers named "blue"): suffix with `-N`
- Output dir doesn't exist: create it (mkdir parents=True)
- Layer count > 99: still zero-pad to 2 digits (3-digit indices
  for > 99 layers — degenerate case)

**Acceptance:**
- Flag exists in --help
- With `--split-layers`, N SVG files appear next to the main output
  (N = number of generated layers)
- Without the flag, no extra files appear
- File naming matches the pattern (test with regex)
- Existing tests don't break

**Files touched:**
- `src/png2svg/core.py` (new helper `render_single_layer_svg`)
- `src/png2svg/cli.py` (add flag, call helper in loop)
- `tests/integration/test_cli.py` (new test)
- `tests/unit/test_core.py` (or new file) for the helper

## Feature 4: ViewBox normalization (`--fix-viewbox`)

**What:** Auto-fix SVG viewBox issues that break Cricut Design Space
imports. The current output uses `viewBox="0 0 W H"` where W, H are
the image dimensions. Some Cricut imports fail when viewBox uses
floats or has a non-zero origin. This flag:
- Rounds W, H to integers
- Sets viewBox to `"0 0 W H"` (always, regardless of scale/offset)
- Optionally offsets coordinates so all positive (default: on)

**CLI:**
```
--fix-viewbox    Normalize viewBox for Cricut Design Space compatibility (default: on)
--no-fix-viewbox    Disable viewBox normalization
```

Wait — argparse convention: store_true for the positive form,
store_false with dest= for the negative form. But that conflicts
with "default: on". Let me reconsider.

**Cleaner design:** Make viewBox normalization **always on by
default**. No flag needed. Just fix the code. This is the kind of
bug fix that should not require user opt-in.

**Implementation:**
1. Find the line in `core.py` that writes the SVG header (likely
   in `_create_layer_groups` or a wrapper that builds the final SVG
   string).
2. Change `viewBox="0 0 {W} {H}"` to use integer-rounded values.
3. Add a unit test that asserts the viewBox is an integer-string
   no-floats format.

**Acceptance:**
- ViewBox in the output SVG uses integer strings
- No new CLI flag (just the fix)
- Existing tests don't break; if any test asserts the old
  viewBox format, update it.

**Files touched:** `src/png2svg/core.py`, possibly
`tests/fixtures/bluey_golden.svg` if viewBox format changed.

**Re-scope: skip this for v1.2.0 if it requires touching the
golden file (the test contract is strict — better to defer the
golden update to its own session).** Make the change in a way
that doesn't affect the golden file.

**Decision rule:** If the change does not affect the golden
file, ship it. If it does, defer to v1.2.1.

## Feature 5: Pen-up travel optimization (`--optimize-travel`)

**What:** Reorder the rendered layers (and within each layer, the
paths) to minimize pen-up travel distance. Currently layers are
output in palette-quantization order (often arbitrary). This
feature uses a nearest-neighbor heuristic: starting from a default
position (e.g. image center, or the bottom-right which is typical
for Cricut's home position), pick the next layer/path whose start
is closest.

**CLI:**
```
--optimize-travel    Reorder layers and paths to minimize pen travel distance
```

**Algorithm:** Greedy nearest-neighbor. NOT optimal (TSP), but for
<100 paths it's good enough and O(N^2) which is fast.

**Implementation hint:** After `process_image_to_hatched_svg`
returns, iterate the layer list. For each layer, the start point
is the first coordinate in its first path. Maintain a "current pen
position" cursor; pick the next layer with the smallest Euclidean
distance from cursor to start point. Within a layer, paths are
already sorted (serpentine, so they're already locally optimized);
don't reorder within a layer for v1.2.0.

**Stats:** Add to `processing_stats`:
- `optimized_pen_lifts`: estimated pen-up count after optimization
- `original_pen_lifts`: estimated pen-up count before
- `travel_distance_saved`: ratio (e.g. 0.15 = 15% less travel)

Actually wait — `processing_stats` already has `legacy_pen_lifts`
and `optimized_pen_lifts` keys (saw them in core.py:887-888). The
counters are already there. Just need to use them.

**Edge cases:**
- Single layer: no-op (already optimal)
- `--optimize-travel` + `--save-session`: the session file
  records the color_map which is order-independent. No conflict.
- Output order changes vs. unoptimized: this **does** change the
  golden file. So this feature requires golden file regeneration.

**Acceptance:**
- Flag exists in --help
- Output layers are reordered (test by checking that layer order
  in output SVG differs from input order, given a synthetic test
  image with known layer positions)
- Existing golden file test must be updated (regenerate
  bluey_golden.svg if --optimize-travel is on by default;
  OR keep --optimize-travel off by default and only update golden
  if user explicitly turns it on)
- **Default: opt-in, NOT on by default**, so existing golden
  file is preserved.

**Files touched:**
- `src/png2svg/core.py` (new function `optimize_layer_order(layers, start=(0,0))`)
- `src/png2svg/cli.py` (add flag)
- `tests/unit/test_core.py` or new file for the algorithm

## Feature 6: Hatch angle per color (`--hatch-angles`)

**What:** Allow different hatch angles per color layer to reduce
visual moiré. Default: 0° (current behavior). With
`--hatch-angles=0,45,90,135` for a 4-color image, layers rotate
their hatch lines by the corresponding angle.

**CLI:**
```
--hatch-angles ANGLES    Comma-separated hatch angles per layer (degrees).
                         If fewer angles than layers, the last value is reused.
                         Example: --hatch-angles=0,45,90,135
```

**Implementation hint:** `RenderParams` already has fields. Add
`hatch_angle: float = 0.0` field. Each layer's hatch generation
needs to apply the angle. The hatch function probably lives in
`_create_layer_groups`. The angle is applied as a rotation
transformation around the layer's center, or by adjusting the
hatch line equation.

**Edge cases:**
- Empty string `--hatch-angles=""`: treat as `[0.0]` (current
  default)
- Non-numeric values: friendly error, exit 1
- Single angle `--hatch-angles=45`: all layers get 45°

**Acceptance:**
- Flag exists in --help
- Default (no flag) behavior is unchanged (golden file preserved)
- With explicit angles, layers in output SVG have rotated hatch
  lines (test by checking the d="..." attributes differ from
  baseline)
- Number of angles < number of layers: last angle is reused

**Files touched:**
- `src/png2svg/core.py` (RenderParams field + hatch function)
- `src/png2svg/cli.py` (add flag, parse comma-separated)
- `tests/unit/test_core.py`

## Cross-cutting requirements

### Tests
Every new feature MUST have at least one positive test and one
negative/error test. Total target: 95+ tests (currently 88).

### Backward compatibility
- **No public API change** to `process_image_to_hatched_svg`,
  `save_session`, `_process_single_layer`, `RenderParams` (the
  RenderParams addition of `hatch_angle` is additive and defaults
  to 0.0, so it's backward-compatible)
- **Default behavior must not change** the output SVG for any
  input. All new features must be opt-in. The golden file
  `tests/fixtures/bluey_golden.svg` must remain valid without
  modification.

### Style
- Follow existing code style (the project uses `ruff format` —
  double quotes, line-length 100ish, 4-space indent)
- Module-private functions use leading underscore
- Type hints on all new public functions

### Version bump
After all features are integrated and tested, bump `__version__`
in `src/png2svg/__init__.py` from `1.1.1` to `1.2.0`. pyproject.toml
uses dynamic version from __init__.py, so just that one file.

Add `[1.2.0] - 2026-06-17` section with all 6 features listed
under `### Added`. Format matches existing entries.

### README
Add a "What's new in 1.2.0" section near the top, but keep it
